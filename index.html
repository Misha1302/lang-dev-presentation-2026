Staging · two different meanings of “once”

There are two different once boundaries

1 · Language environment

WistEngine.Create(...) → LanguageDefinition → LanguageCompiler → LanguagePlan → LanguageRuntime

Whole-language composition is resolved once for that engine.

2 · Compiled program

Compile<TDelegate>(code) → Runtime.Build(...) → durable program → reusable delegate

This is a different reuse boundary.

WistEngine.CreateEnvironment reuse ≠ compiled-program reuse.

Decision rule

Use a planner only when cross-stage variability pays for it

Prefer a smaller mechanism

stable pipeline → handwritten wiring
independent options → builder/config
object lifetime/substitution → DI
optimizer pass execution → pass manager
IR legalization → dialect conversion

Planning earns its cost when…

independently owned language choices interact across stages and no local owner can select the whole executable pipeline.

Choose the smallest mechanism that owns the real decision.

Positioning, not a superiority claim over LLVM, MLIR, DI, builders or language workbenches.

Appendix · DI / builder

Why isn't this just Dependency Injection?

Builder / DI

Excellent when the host already knows what to instantiate and wire.

Planning

Adds an explicit phase for whole-language dependencies, conflicts, provider ambiguity, ordering and artifact routes.

Boundary

UT can still use ordinary objects and DI-like construction after the global decisions are resolved.

The distinction is ownership of global composition decisions, not “DI is bad”.

Appendix · prior art

Why not LLVM / MLIR / a language workbench?

LLVM

Excellent compiler infrastructure and pass management once the relevant compiler/IR composition is defined.

MLIR

Extensible multi-level IR with dialects, operations, types and conversion infrastructure.

Racket / MPS

Richer language-oriented ecosystems and workbench models at different layers.

This talk

Whole runnable-language composition → explicit immutable plan → exact runtime materialization.

Positioning only. No novelty or superiority claim.

Appendix · deterministic routing

Deterministic selection is a protocol property, not semantic equivalence

A route can be deterministically selected from expressed contracts and planning cost while two implementations still differ semantically.

Equal-cost/tie behavior and provider preferences belong to the planning protocol and should be tested as such. Route Cost is not execution-time performance.
