Planner/runtime boundary

Runtime executes the plan; it does not rebuild the language

Planner

  • resolve features + contributions
  • select capability/runtime providers
  • apply ordering + conflicts
  • build artifact routes
  • emit immutable LanguagePlan

Runtime

  • verify exact plan/provider match
  • materialize planned components
  • assemble selected route
  • Run(request)
  • report execution failures

No second global composition pass.

Cost model

Extensibility changes where we pay — not whether cost exists.

1 · Planning

resolve providers / conflicts
order + route search
canonicalize + diagnose
time + allocations

2 · Runtime creation

verify immutable plan
materialize components
assemble selected route
construct sessions

3 · First execution

parse / lower / codegen where applicable
initialize providers
JIT / cold caches
first-use costs

4 · Steady state

execute concrete selected path
no global re-planning by architecture
dispatch / validation / allocations may remain

Don't repeatedly pay for decisions already made.

No re-planning ≠ zero overhead · plus protocol/versioning/testing cost · benchmark each boundary separately

Takeaway

Be extensible when composing. Be concrete when executing.

Extensions describe possibilities.
Planning resolves one LanguagePlan.
Runtime executes the resolved language.

Global composition decisions do not need to remain dynamic during repeated execution.

Architecture takeaway · not a claim that every remaining runtime abstraction disappears
