Start with the central contrast: this is not another plugin hook. The main idea is that the language and the compiler pipeline are assembled from modules.

Use simple wording: modules can contribute syntax, facts, analyses, transformations, and backend information.

Slide 3 speaker notes

So, the language is a small core plus a set of modules. The stable core provides the common mechanisms. Modules provide the actual language semantics.

The important point is that the core does not need to know what kinds of semantic information we may add in the future. The configuration only registers what exists right now.

Now let us look at a concrete rule for deciding whether vectorization is safe. If all required facts hold, then the rewrite is safe.

But safe does not mean useful. Vectorization may be correct and still make the program slower, so we need a separate heuristic or cost model.

Slide 6 speaker notes

We stay with the same vectorization example. One premise of the old vectorization rule is that the loop body is pure, so the consumer asks for Pure(Body(L)).

The pseudocode is architectural, not final API syntax. The engine finds rules that can produce the requested relation, filters them by applicability, recursively asks for their premises, then hands successful derivations to an explicit resolution policy. That policy matters when there are multiple proofs or conflicting knowledge; this slide deliberately does not define a universal policy.

The graph on the right is one accepted derivation. Leaves come from ordinary analyses, the bridge combines them, and the result keeps provenance.

Slide 8 speaker notes

This is the same idea from the architectural side. Producers do not expose feature-specific callback APIs to every consumer. They publish semantic facts and rules into a common mechanism.

The pseudocode is deliberately small: publish knowledge, compose knowledge, query knowledge. The core owns the mechanism and provenance; modules own the actual analyses and the correctness of their produced facts.

Slide 9 speaker notes

This is the concrete compiler example. The simplified SIMD rule was already written in terms of semantic premises: independent iterations, purity, and target support. A production rule may have more conditions, but the architectural point is the same.

Later, a dependency or parallelism module adds a new rule proving IndependentIterations from its own facts. The first rule is unchanged. It does not need to know where IndependentIterations came from.

Next, we generalize this pattern: new vocabulary creates new proof paths while existing semantic contracts remain valid.

Slide 10 speaker notes

This is why provenance matters in practice. Suppose purity is proven but IndependentIterations is not, because dependency analysis found a cross-iteration dependence. The vectorizer does not simply receive a mysterious false value; the decision has an inspectable semantic path.

That helps diagnostics, compiler debugging and architecture evolution. It also makes the shared mechanism easier to justify: the same relation-oriented interface used for composition becomes the explanation surface for decisions.

Slide 11 speaker notes

The DAG does not mean the shared layer proves arbitrary programs correct. Hard work such as alias analysis, dependence analysis or effect analysis remains ordinary compiler code.

Those analyses publish facts and evidence. The shared layer connects facts through explicit, applicable rules and preserves provenance so consumers can understand where an answer came from.

This boundary is deliberate: the goal is semantic infrastructure for modular compilers, not Lean or Coq inside the optimizer.
