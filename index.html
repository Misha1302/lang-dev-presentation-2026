Planner/runtime boundary

  • assemble selected route

Deabstraction, precisely

Planning removes uncertainty, not necessarily interfaces

Open before planning

capability → provider A | B route → r1 | r2 order → partial constraints runtime → candidate set

Frozen in LanguagePlan

provider → exact identity route → exact steps + cost order → deterministic sequence runtime → exact provider / policy

The planner deabstracts global choices. Objects, interfaces and dispatch may remain.

Architectural guarantee: resolved composition data · performance is a separate claim
Two deabstraction layers

Staging is guaranteed; representation specialization is optional

1 · Composition deabstraction

candidate sets → concrete identities
route search → concrete route
partial order → concrete sequence
global choice is not repeated during execution

2 · Representation/code specialization

known slot / type / provider may enable simpler representation, fewer lookups or devirtualization — depending on implementation and JIT/AOT.

Do not infer layer 2 from layer 1 without measurement.

Layer 1 = current architecture · Layer 2 = optimization opportunity

Takeaway

Extensibility is not just making components pluggable

When independent components must form one language, someone has to own global composition decisions.

Keep local knowledge local.
Make global decisions explicit.
Then execute the resolved plan.

Architecture takeaway, not framework advocacy
