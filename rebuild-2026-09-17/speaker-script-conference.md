## m1

I want to argue for a deliberately narrow version of Extensible Programming. Not “install a framework and every language becomes free,” and not “replace the compiler with a graph of plugins.” The claim is smaller and, I think, more testable: a language feature can be authored against explicit semantic requirements instead of one concrete implementation, those requirements can be resolved when we build one concrete language, and some of the generic machinery can later disappear when the concrete program establishes the right legality conditions. That is why the title has two halves. First, build the language from independently authored pieces. Then, once the language and the program are concrete, remove authoring abstractions that no longer need to survive. I will use one running feature—delegates and lambdas—to keep the whole story grounded. The question throughout is not “can we add another extension point?” It is: where do we put the semantic boundary so that composition stays precise and later specialization stays safe?

## m2

Start from the programmer, not from the framework. Imagine I install an independently authored Delegates extension. I can now write a named callable shape, assign a lambda to it, and invoke it. That changes the source language. The programmer gained a new construct: callable values, lambda creation, invocation, and potentially captured environments. This is the first reason I call the problem Extensible Programming rather than just compiler extensibility. A compiler pass that nobody can name in the source language is not enough for this example. Here the feature changes what programs are expressible. And because it is programmer-visible, the feature has to survive more than parsing. It has to participate in typing, lowering, tooling, optimization, and backend decisions. So before I show any planner or semantic machinery, keep this tiny program in mind. We are trying to author this feature once without secretly assuming one fixed type system underneath it. That creates the next problem.

## m3

A normal compiler plugin usually extends a pipeline whose language and representation are already known. That is useful, but it is a different contract. A language feature extension changes the language itself, so it touches several owners at once. The parser must recognize new forms. Typing must decide what a callable value means. Lowering must choose a representation. Tooling must understand the new construct. Optimization must know what it may erase or preserve. If I write Delegates only against one compiler’s private type objects, then I have not really authored a reusable language feature; I have authored one integration. So the important transition is from “this compiler accepts a plugin” to “this feature can participate in several concrete languages.” The moment we demand that, the dependency on type semantics becomes visible. The same syntax can be perfectly reasonable under several different typing models. That is the first coupling we need to break without losing precision.

## m4

Take the same delegate feature and place it in three language profiles. In a nominal profile, 'Mapper' may be a named delegate type with identity of its own. In a structural profile, there may be no special named delegate identity at all—the relevant type may simply be a function from 'Int' to 'String'. In a gradual profile, the static callable type may coexist with a runtime contract or check. The surface feature still looks like “make a callable value and invoke it,” but the semantic answers differ. Representation differs. Assignability can differ. Variance can differ. Whether a runtime check is required can differ. Even capture legality can differ once ownership or effects enter the picture. None of these models is the one universal truth that Delegates should hardcode. So the reusable feature needs a way to ask the semantic questions it actually depends on while allowing the concrete language to decide how those questions are answered.

## m5

The obvious engineering response is pairwise integration. Write 'DelegatesForNominalTypes', then another adapter for structural types, another for gradual types, and later more combinations for effects, ownership, or another backend. This can be completely reasonable for a small product. But as an extensibility model it has a scaling problem: feature authors and semantic-system authors become coupled pairwise. Every new dimension creates private glue. The important issue is not just the raw number of files. The issue is ownership. Who knows the complete matrix? Who updates every adapter when a semantic contract changes? Which adapter is authoritative when two disciplines constrain the same operation? At some point the “reusable feature” is reusable only because one central team maintains all combinations. So pairwise adapters are my first strongest baseline: simple, local, often correct. The architecture I am proposing only wins if it reduces that coupling without hiding semantic differences behind a weaker common denominator.

## m6

The second tempting answer is a giant 'ITypeSystem'. Give the feature one universal interface and put every semantic operation there: assignability, callable construction, capture legality, effects, lifetimes, conversions, maybe layout and runtime checks. This looks modular at first because Delegates depends on one interface. But the coupling has only moved. If the interface grows to contain every future question, it becomes a universal type system designed by the framework. If it stays small, then real language differences leak into casts, side channels, special tags, or “optional” escape hatches. Both outcomes are bad for independent authorship. So I do not want Delegates to depend on “the type system” as a god object. I want it to depend on the specific semantic capabilities needed by this feature. That shifts the design question from “what methods must every type system implement?” to “what questions does this consumer need answered, and which components are allowed to answer or constrain them?”

## m7

For the delegates example, the candidate contract is intentionally small. The feature may need to ask: can a callable representation be constructed for this signature? Is one value assignable to the target callable type in this context? Is this callable applicable to these arguments? What result type does invocation produce? Is capturing this variable legal in this closure under the active ownership or lifetime rules? Does a conversion require a runtime check? Notice what I am not claiming. This is not a universal ontology of all type systems. It is not a promise that six operations model every callable feature. It is the minimum semantic vocabulary required by this running example so that we can test the architecture. The key idea is demand-driven dependency: the feature declares the questions it needs. Concrete semantic components provide or constrain answers. If a required question has no valid provider, composition must fail rather than invent an answer.

## m8

There are actually two different reuse problems, and conflating them makes the architecture look easier than it is. Scenario A is reuse across alternative profiles: the same Delegates feature can live in a nominal language or a structural language or a gradual language. Scenario B is harder: one concrete language can combine several independently authored typing disciplines at the same time. Nominal types may own the representation of 'Mapper'. An effect system may constrain whether a target can be invoked in the current context. An ownership system may constrain whether a captured reference may outlive the stack frame. Now there is no single object called “the type system” that owns the whole answer. The result is jointly constrained. So the composition mechanism must support more than provider selection. It must make responsibilities explicit and detect when independently authored constraints cannot be satisfied together. That creates the next problem: who owns each legality condition?

## m9

My proposed boundary is that the feature owns the semantics of the feature, while semantic disciplines own or constrain the properties that belong to them. Delegates owns the fact that there is a callable construct, a signature, a creation form, an invocation form, and potentially an environment capture shape. A nominal type component may own the named representation and nominal assignability relation. An effect component may constrain call compatibility. Ownership may constrain capture and lifetime legality. A gradual typing component may say a runtime check is required instead of rejecting the conversion statically. This sounds almost obvious, but it gives us an important rule: no producer may silently weaken the consumer’s legality condition. If delegate lowering needs “callable target is exact and capture is legal,” then receiving “probably callable” from one subsystem is not enough. The consumer owns the obligation. Producers contribute evidence toward it. That distinction will matter again when we get to optimization.

## m10

Now I want to separate two timescales that are easy to mix up. At global or profile time, we are deciding what language we are building. Which providers are present? Which representation is selected? Which contracts are compatible? Which routes exist? Which backend policy applies? Those are language-configuration decisions. At local or per-program time, we learn facts about one concrete program point: the exact target of this delegate, the actual capture set, whether the value escapes, which effects occur, which lifetime relations hold. A globally resolved language tells me that delegate programs have a coherent implementation. It does not tell me that this particular delegate invocation can be rewritten into a direct call. That would be a category error. Global resolution closes the set of semantics available to the compiler. Local analysis establishes transformation-specific facts. Keeping those apart prevents us from claiming “the language composed successfully, therefore this optimization is sound.”

## m11

So what does the global resolver do? Suppose the requested profile contains Delegates, nominal types, effects, and ownership. The resolver must choose or bind providers for the capabilities the feature requires, verify contract compatibility, order components when order matters, and reject conflicts that cannot be reconciled. Importantly, it closes an open authoring world into one concrete compiler configuration. Before resolution, new independently authored components may appear. After resolution, the compiler works against a finite selected set. And this must fail closed. If the ownership component cannot answer capture legality for an escaping closure, the resolver cannot silently decide that capture is fine. It either rejects the profile, rejects that construct, or chooses a generic implementation whose requirements are actually satisfied. “Extensible” does not mean “optimistically assume the missing semantics.” It means the failure becomes explicit and local to a declared requirement.

## m12

At this point we have solved structural composition, but not semantic correctness. We may have a parser for delegate syntax, a provider for callable types, a lowering route, and a backend. All of that can assemble and execute. But now imagine an optimizer replacing a generic delegate invocation with a direct call. Structural success tells us almost nothing about whether that rewrite is legal. The delegate might point to several targets. It might carry an environment. A conversion might require a runtime check. An effect or lifetime constraint might be observable. This is the second coupling in the talk. The transformation wants facts produced by several semantic components, but it should not import all of their private APIs. So the transformation states its own proof obligation. Other components may contribute evidence. The transformation decides whether that evidence is sufficient. Structural composition gets us a compiler. Proof obligations decide which abstractions may safely disappear.

## m13

Here is a concrete specialization obligation. We start with a value 'f' of delegate type 'Mapper', created from a lambda that calls 'Foo', and later we invoke 'f(42)'. To replace this with 'Foo(42)', the transformation needs more than “f is callable.” It needs an exact target, or an equivalent proof that the invocation resolves to 'Foo'. The signature and conversions must match the original delegate call. Captures must be absent or legal under the chosen representation. Effects must remain compatible. Lifetime obligations must still hold. If the generic delegate path would have performed a runtime check, the rewrite must account for that check or prove it unnecessary. And if the optimization assumes the delegate does not escape, non-escape becomes part of the obligation. The list belongs to the transformation. If one required proposition is missing, we keep the safe generic path.

## m14

This slide is my anti-hand-waving rule. Every semantic dependency should be expressible as producer, fact, consumer, and use. For example, the nominal type component may establish that the lambda value is assignable to 'Mapper' under a particular conversion context. The effect system may establish that calling 'Foo' is allowed here. Escape or capture analysis may establish that the delegate has an exact target and that the environment does not escape. Delegate lowering then consumes those facts to discharge a direct-call obligation. The benefit is not that we invented facts—compilers already have analyses and semantic results. The benefit would be an ownership boundary that lets independently authored components exchange the particular results required by another component without centralizing every semantic rule in one API. If a fact has scope or assumptions, those must travel with it. Otherwise we merely replaced hidden coupling with misleading metadata.

## m15

Fail-closed behavior also requires more than a boolean “known.” There are several materially different states. 'Established(P)' means the current evidence is strong enough to discharge proposition P. 'Unknown(P)' means we do not know; the optimization keeps the generic path. 'Unsupported(P)' means the selected language configuration cannot even produce the required kind of evidence; that may be a profile-level incompatibility. 'Refuted(P)' means the proposition is false and the rewrite is illegal. And contradictory current evidence is different again: two components appear to assert incompatible facts. Unless the language defines a trusted reconciliation rule, contradiction must fail closed. I am not arguing that every compiler needs exactly five enum values. I am arguing that extensibility makes epistemic state part of the interface. If “no answer” and “false” are collapsed, either valid programs get rejected or unsafe rewrites become possible.

## m16

Facts also change over time, because the program representation changes. An analysis may derive “delegate target is exactly Foo” on one IR. A lowering pass may replace the delegate node with another representation. An optimization may clone or move code. A later pass may mutate control flow. So semantic evidence needs a lifecycle: derive it under explicit scope and assumptions, transport it only when there is a valid representation mapping, preserve it when a transformation proves preservation, recompute it when necessary, and invalidate it when its assumptions no longer hold. LLVM already has analysis preservation and invalidation ideas; MLIR has interfaces, effects, legality, and explicit conversion machinery. I am not claiming novelty for those mechanisms. The research question is whether language-feature composition can expose a similarly disciplined evidence boundary early enough that later deabstraction can consume it without learning every producer’s implementation details.

## m17

Now the title becomes visible in code. Before specialization, the compiler may need a generic delegate value carrying a signature, a target, maybe an environment, a generic 'InvokeDelegate', and perhaps a runtime adapter or check. That machinery is valuable while the language is open and the program facts are incomplete. After we select one concrete language and analyze one concrete program point, some of it may become unnecessary. If the target is exactly 'Foo', the environment does not need generic handling, the conversions match, and the required effect and lifetime obligations hold, then this call site can become 'Foo(42)'. The generic authoring abstraction disappears locally. What remains is the concrete operation and the semantics that must be preserved. This is not a promise of zero runtime cost. It is a conditional transformation: when proof succeeds, erase; when proof is unknown or refuted, retain the generic delegate path.

## m18

This proposal only matters if it survives strong alternatives. First, language workbenches and extensible typing frameworks already compose syntax and typing rules. If your problem is fully handled there, use them. Second, MLIR-style interfaces, effects, legality checks, and conversion frameworks already provide excellent mechanisms for modular compiler semantics. If ordinary interfaces plus explicit adapters are enough, that is probably the simpler engineering choice. Third, a small adapter per type system may be cheaper than inventing a shared capability layer. That baseline should not be dismissed. So the hypothesis is not “existing systems cannot do composition.” The hypothesis is that there is a useful boundary where a feature can depend on semantic capabilities, multiple independent disciplines can jointly constrain those capabilities, and later transformations can consume explicit evidence without introducing a central universal type system. If that boundary adds more ceremony than coupling it removes, the experiment fails.

## m19

After that attack, the research hypothesis is much narrower than the original ambition. The question is: can a language feature depend on semantic capabilities rather than one concrete type-system implementation, can those capabilities be globally resolved when the language combines independently authored semantic components, and can later specialization use program-specific evidence to remove generic machinery only when legality is established? None of the ingredients is novel by itself. Modular language composition exists. Capability-style interfaces exist. Analysis invalidation exists. Proof obligations exist. Translation validation exists. The possible contribution is the disciplined connection between these phases and ownership boundaries: author the feature against explicit semantic questions; close the world into a concrete profile; track evidence with scope and validity; let the consumer own the rewrite obligation. That is falsifiable. If pairwise adapters are consistently simpler, or capability contracts lose precision, or evidence exchange cannot remain stable across representations, then this architecture is not worth it.

## m20

Where does UniversalToolchain fit? As evidence, not as the thesis. The current implementation can witness selected pieces of the argument: declarative language profiles, staged planning, a resolved plan that can be snapshotted, selected cross-backend parity, route feasibility checked before preference, and bounded examples where generic machinery becomes more concrete. Those are useful because they stop the talk from being pure architecture fiction. But I need to state the boundary clearly: Delegates reused across multiple independently authored type semantics is still a target and research hypothesis. I am not claiming that UT already implements this complete capability contract. I am also not using benchmark smoke as performance evidence. The right way to read UT here is: some structural mechanisms and local deabstraction ideas are implemented witnesses; the general semantic-composition boundary is what still has to be designed, tested, and potentially falsified.

## m21

So the entire talk reduces to four verbs: extend, resolve, prove, erase. Extend the language with a programmer-visible feature authored against explicit semantic requirements. Resolve those requirements into one concrete language profile and fail closed when the profile cannot support them. Prove local obligations for a particular program point using current evidence from the components and analyses that actually own those facts. Then erase only the generic machinery whose obligations were established. In the delegate example, what may disappear is generic invocation, adapters, or environment machinery at a proven call site. What necessarily remains is the concrete call and the preserved observable semantics. What is implemented today is a collection of bounded witnesses in UniversalToolchain. What remains research is the general capability boundary across independent type semantics and the evidence lifecycle that makes safe deabstraction possible. If that boundary cannot beat ordinary adapters in precision and engineering cost, we should reject it. That is the experiment I want to run.
